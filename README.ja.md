`kanna` コマンドは、[kanna](https://go-kanna.github.io/ja/) コードジェネレータファミリーを、必要な順序で実行します。パッケージの一覧をプロジェクトで持つ必要がなくなります。vet のあるジェネレータの vet もまとめて実行するので、その一覧も要りません。設定は増えません。実行するのは、すでにある `//go:generate go tool kanna-*` の行です。各ジェネレータは、このコマンドがなくても今までどおり動きます。

## インストール

```sh
go get -tool github.com/go-kanna/kanna
```

実行するジェネレータは、`-deps` に答えられ、モジュールが選ぶ go-kanna/internal でビルドできるリリースである必要があります。そうでないものがあれば `kanna gen` と `kanna vet` が伝えます。選ばれる go-kanna/internal は、新しい kanna やジェネレータを入れると上がることがあります。モジュールのツールをまとめて上げるには、次のようにします。

```sh
go get tool
```

`go tool kanna -version` は kanna の版を表示します。各ジェネレータの `-version` と同じです。

## 使い方

```text
$ go tool kanna gen
  internal/feature/todo/model/todo_model.go:15      kanna-value      wrote internal/feature/todo/model/value_gen.go
  internal/feature/todo/model/todo_model.go:42      kanna-fixture    unchanged
  internal/feature/todo/usecase/generate.go:3       kanna-validator  wrote internal/feature/todo/usecase/validator_gen.go
  ...
11 tasks, 2 files changed
```

何もすることがなければ `11 tasks, 0 files changed` の一行だけです。task が失敗すると、その task の後に実行する task だけを止めます。後に実行する task とは、`-plan` が `after:` で示すつながりを、直接または間接にたどれる task です。止めた task は表に `not run` と出し、待っていた失敗した task を添えます。ほかの task は、`go build` が壊れたパッケージを import しないパッケージのビルドを続けるのと同じく、そのまま実行します。そのため、1 回の実行ですべての失敗が分かります。終了コードは 1 です。task が書いたものは、失敗した task が途中まで書いたものも含めて、作業ツリーに残ります。

```text
completed    internal/feature/todo/model/todo_model.go:15      kanna-value   wrote internal/feature/todo/model/value_gen.go
failed       internal/feature/todo/mapper/todo_mapper.go:10    kanna-mapper
  internal/feature/todo/mapper/todo_mapper.go:32:13: error: cannot use "x" (untyped string constant) as int value in …
not run      internal/feature/todo/handler/todo_handler.go:15  kanna-di      after failed internal/feature/todo/mapper/todo_mapper.go:10
completed    internal/messages/generate.go:3                   kanna-i18n    wrote internal/messages/i18n_gen.go

2 completed, 1 failed, 1 not run
2 files changed; completed changes remain in the working tree
```

ジェネレータが表示するものは、その task の行の下に stderr へ出し、報告は stdout に出します。そのパスは、ジェネレータが動くパッケージからではなく、go コマンドと同じく `kanna gen` を実行した場所から辿れる形です。報告と `-plan` のパスも同じです。

go コマンドと同じくパッケージで絞り込めます。既定は `./...` です。指定したパッケージが読むものを書く task は一緒に実行し、それを読む task は実行しません。`-tags` は go コマンドと同じくカンマ区切りのビルドタグを受け取ります。そのタグで、どのファイルの `//go:generate` の行を実行するかを選び、各ジェネレータにも渡してパッケージの読み込みに使わせます。

`kanna gen` と `kanna vet` は、実行した場所を含むモジュールを対象にします。それ自体はモジュールでない `go.work` のワークスペースのルートでは、モジュールが見つかりません。ワークスペースのモジュールごとに、そのモジュールの中で実行してください。

`go tool kanna gen -plan` は、何も実行せず、実行するものとその順序の理由を表示します。

```text
$ go tool kanna gen -plan
...
8. internal/feature/todo/usecase/generate.go:3
   run:    go tool kanna-validator
   writes: internal/feature/todo/usecase/validator_gen.go
   after:  5 — reads internal/feature/todo/scopes, which kanna-orm writes into
   after:  7 — reads internal/messages, which kanna-i18n writes into

9. internal/feature/todo/usecase/generate.go:4
   run:    go tool kanna-di
   writes: internal/feature/todo/usecase/di_gen.go
   after:  2 — its tests read internal/di, which kanna-di writes into
   after:  4 — its tests read internal/feature/todo/model/fixture, which kanna-fixture writes into
   after:  6 — its tests read internal/feature/todo/postgres, which kanna-orm writes into
   after:  8 — code in internal/feature/todo/usecase calls what kanna-validator generates
...
external prerequisites:
  internal/gen/showcase/todo/v1 — generated by protoc-gen-go, protoc-gen-go-grpc
```

`go tool kanna gen -check` は、ディスク上の内容と生成される内容を比較し、何も書き込みません。差分のあるファイルがあるとき、および検査できなかった task があるときに失敗します。検査できないのは、差分のある task が書くものを読む task です。

```yaml
- run: go tool kanna gen -check
```

`-check` が示すのは差分のあるファイルで、差分の中身は表示しません。CI で中身を読むには、実際に生成して、git で差分を表示します。この方法なら、`-check` が検査できなかった task の変更も差分に出ます。`git add -AN` は、まだコミットされていないファイルも `git diff` に表示させるためのものです:

```yaml
- run: go tool kanna gen && git add -AN && git diff --exit-code
```

環境変数 `KANNA_CHECK=1` は、各ジェネレータと同じく `-check` と同じ動きをします。どちらも `-plan` とは一緒に使えません。

### 実行するもの、しないもの

task は `//go:generate go tool kanna-*` の一行で、`go generate` と同じように実行します。パッケージのディレクトリで、`GOFILE` などの環境変数付きで実行し、行の引用符や `$` の変数も同じように読みます。同じパッケージに同じ行が二つあれば、一回だけ実行し、二つ目以降の行で警告します。`go generate` なら、無駄にもう一度実行するからです。

次の計画は、開始する前に拒否します。task が互いを待っているもの、二つの task が同じファイルを書くもの、入力が存在しないもの、そしてジェネレータを別の形で実行しようとする行があるものです。別の形とは、`-command` エイリアス、シェル、別の実行ファイル、名前の代わりのパッケージのパス（`go tool kanna-value` の代わりの `go tool github.com/go-kanna/value/cmd/kanna-value`）、`kanna-orm describe`、`kanna-value vet` などのジェネレータの `vet` です。vet はコードを検査するだけで何も書かず、`kanna vet` が実行します。他のジェネレータの行には触れません。buf や sqlc が書くものは先に用意しておく必要があり、その検査もそれぞれのツールの役目です。

kanna ファミリーのどのジェネレータのキーでもない `//kanna:` の行（`//kanna:container` のつもりの `//kanna:di` など）は警告します。どのジェネレータも読み飛ばし、ほかのジェネレータの分まで知らせることはできないからです。あるジェネレータのキーの行は、そのジェネレータに任せます。宣言に付いていない行と、キーの打ち間違いは、そのジェネレータが警告します:

```text
internal/feature/todo/handler/todo_handler.go:14:1: warning: //kanna:di is a directive of no kanna generator
```

## 生成物を呼ぶコードを検査する

kanna-value、kanna-orm、kanna-i18n には、それぞれ vet があります。生成物を呼ぶコードのうち、コンパイラが通してしまう誤りを見つけます。`go tool kanna vet` は、モジュールの `//go:generate` の行が実行するジェネレータのうち、vet のあるものの vet を実行します:

```text
$ go tool kanna vet
# kanna-value
internal/feature/todo/usecase/put_todo_use_case.go:42:17: error: "hgih" is none of the constants of model.Priority
  did you mean model.PriorityHigh?
```

vet の報告は、`go vet` がパッケージごとにするのと同じく、その vet の名前の行の下に stderr へ出します。どの vet も何も見つけなければ、何も表示しません。エラーを見つけた vet があれば失敗しますが、残りの vet も実行します。vet は `kanna vet` を実行した場所で、指定したパッケージ（既定は `./...`）に対して実行し、`-tags` はそれぞれに渡します。どの vet を実行するかを決める `//go:generate` の行も、vet が読むファイルと同じく、そのタグで選んだファイルから探します。

どの vet を実行するかはモジュール全体で決めるので、`go tool kanna vet ./internal/feature/todo/usecase` のように、自分の `//go:generate` の行がないパッケージにも vet を実行します。実行する前に、それぞれのバージョンを確かめます。モジュールのツールでないジェネレータや、vet より前のリリースがあれば、`kanna gen` が計画の問題で止まるのと同じく、どの vet も実行しません。

vet は、生成物をディスク上のまま、つまりコンパイルされるものを読みます。それが最新かどうかは `kanna gen -check` の役目です。CI では両方を実行します:

```yaml
- run: go tool kanna gen -check
- run: go tool kanna vet
```

通っても、vet が見つけた誤りがなかったというだけで、誤りがないことの証明ではありません。

## 順序の決まり方

各ジェネレータは、`-deps` に対して一回の実行が読むものと書くものを答えます。どのパッケージが何を import するかは、モジュールの手書きのファイルからわかります。task は、自分が読むパッケージに書き込む task の後に実行します。順序を決めるのに、ジェネレータが書いたものは使わないので、ジェネレータの実行前でも実行後でも計画は変わりません。

二つの task が、どちらも読むパッケージに書き込むときは、コードが何を呼んでいるかで順序を決めます。task は出力を置いた後でそのコードを検査するので、コードが呼ぶものを書く task の後に実行します。コードが両方の書くものを呼んでいると、どの順序でもコンパイルが通らず、`go generate` では何もない状態から生成できません。`kanna gen` は片方を先に実行し、もう一方の名前がこれから書かれることを伝えます。最後に実行する task は、その名前が揃っていなければ、エラーとして報告します。

## ファミリーの開発

[`DEVELOPING.md`](DEVELOPING.md) には、複数のリポジトリにまたがる変更のしかたを書いています。[`dev`](dev) にある全チェックアウトのワークスペース、それに対して全リポジトリのテストを実行するスクリプト、リリースの順序です。

## このモジュールの以前のバージョン

`github.com/go-kanna/kanna` は、以前は別のモジュール（kanna v0.2.x と初代の kanna-orm）でした。そのバージョン v0.0.1 から v0.2.0 は Go モジュールプロキシに残っていますが、取り下げてあるので `go get` が警告を出します。コードはサイトのリポジトリの [`archive/v0.2`](https://github.com/go-kanna/go-kanna.github.io/tree/archive/v0.2) ブランチにあります。`kanna` コマンドは、それより上の v0.3.0 から始まります。
