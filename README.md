# kanna

[![日本語](https://img.shields.io/badge/lang-%E6%97%A5%E6%9C%AC%E8%AA%9E-blue.svg)](README.ja.md)

The `kanna` command runs the [kanna](https://go-kanna.github.io/) family of Go code generators in the order they need,
so that a project keeps no list of packages for it, and their vets, so that it keeps no list of those either. It adds
no configuration: what it runs is the `//go:generate go tool kanna-*` lines already there, and each generator goes on
working without it.

## Install

```sh
go get -tool github.com/go-kanna/kanna@latest
```

Each generator it runs has to be a release that answers `-deps` and builds with the go-kanna/internal the module
selects, which a newer kanna or generator can raise; `kanna gen` and `kanna vet` tell you when one is not. To update
every tool of the module at once:

```sh
go get tool
```

`go tool kanna -version` prints the version of kanna, as `-version` does for each generator.

## Usage

```text
$ go tool kanna gen
  internal/feature/todo/model/todo_model.go:15      kanna-value      wrote internal/feature/todo/model/value_gen.go
  internal/feature/todo/model/todo_model.go:42      kanna-fixture    unchanged
  internal/feature/todo/usecase/generate.go:3       kanna-validator  wrote internal/feature/todo/usecase/validator_gen.go
  ...
11 tasks, 2 files changed
```

With nothing to do it says `11 tasks, 0 files changed`, and no more. The first task to fail stops the run, and what the
tasks before it wrote stays:

```text
completed    internal/feature/todo/model/todo_model.go:15    kanna-value   wrote internal/feature/todo/model/value_gen.go
failed       internal/feature/todo/mapper/todo_mapper.go:10  kanna-mapper
  internal/feature/todo/mapper/todo_mapper.go:32:13: error: cannot use "x" (untyped string constant) as int value in …
not run      internal/feature/todo/handler/todo_handler.go:15  kanna-di

1 completed, 1 failed, 1 not run
1 file changed; completed changes remain in the working tree
```

What a generator says goes to stderr, below its task, and the report to stdout. Its paths lead from where `kanna gen`
runs, as the go command's do, rather than from the package the generator runs in, and so do those of the report and of
`-plan`.

Packages narrow it down, as for the go command. `./...` is the default. The packages bring along what writes what they
read, and not what reads them.

`go tool kanna gen -plan` prints what would run, and why in that order, running nothing:

```text
$ go tool kanna gen -plan
...
8. internal/feature/todo/usecase/generate.go:3
   run:    go tool kanna-validator
   writes: internal/feature/todo/usecase/validator_gen.go
   after:  5 — reads internal/feature/todo/scopes, which kanna-orm writes into
   after:  7 — reads internal/messages, which kanna-i18n writes into

9. internal/feature/todo/usecase/generate.go:4
   run:    go tool kanna-di
   writes: internal/feature/todo/usecase/di_gen.go
   after:  2 — its tests read internal/di, which kanna-di writes into
   after:  4 — its tests read internal/feature/todo/model/fixture, which kanna-fixture writes into
   after:  6 — its tests read internal/feature/todo/postgres, which kanna-orm writes into
   after:  8 — code in internal/feature/todo/usecase calls what kanna-validator generates
...
external prerequisites:
  internal/gen/showcase/todo/v1 — generated by protoc-gen-go, protoc-gen-go-grpc
```

`go tool kanna gen -check` compares what is on disk with what would be generated, and writes nothing. It fails on a
file that differs, and on a task it could not check, which is one that reads what a differing task would write:

```yaml
- run: go tool kanna gen -check
```

`-check` names what differs, not how. To read the differences in CI, generate and ask git instead, which also follows a
change through the tasks `-check` could not check. `git add -AN` has `git diff` show a file no commit has yet:

```yaml
- run: go tool kanna gen && git add -AN && git diff --exit-code
```

### What it does and does not run

A task is one `//go:generate go tool kanna-*` line, run as `go generate` runs it: in its package's directory, with
`GOFILE` and the rest, and with the line's quotes and `$` variables read the same way. The same line twice in a package
runs once, with a warning at each line after the first, which `go generate` would run again for nothing.

Before starting, it refuses a plan with tasks waiting for each other, two tasks writing one file, an input that is not
there, or a line that means to run a generator some other way: a `-command` alias, a shell, another executable,
`kanna-orm describe`, or the `vet` of a generator, such as `kanna-value vet`, which checks code and writes nothing, and
which `kanna vet` runs. Other generators' lines it leaves alone, so what buf or sqlc write has to be there first, and is
theirs to check.

It warns about a `//kanna:` line whose key no generator of the family has, such as `//kanna:di` for `//kanna:container`,
which each generator passes over and none can tell for the others. A line of a generator's own key it leaves to that
generator, which warns about one no declaration holds and about a typo of its key:

```text
internal/feature/todo/handler/todo_handler.go:14:1: warning: //kanna:di is a directive of no kanna generator
```

## Checking the code that calls what they write

kanna-value, kanna-orm, and kanna-i18n each come with a vet, which finds what the compiler lets through in the code
calling what they write. `go tool kanna vet` runs the vet of each generator that the module's `//go:generate` lines run
and that has one:

```text
$ go tool kanna vet
# kanna-value
internal/feature/todo/usecase/put_todo_use_case.go:42:17: error: "hgih" is none of the constants of model.Priority
  did you mean model.PriorityHigh?
```

What a vet reports goes to stderr, below a line naming it, as `go vet` does for a package, and nothing is printed when
no vet finds anything. A vet that finds an error fails the run, and the others run all the same. The vets run where
`kanna vet` runs, on the packages given, `./...` by default, and `-tags` goes to each of them. The tags also choose the
files whose `//go:generate` lines tell which vets run, as they choose those the vets read.

Which vets run is told by the whole module, so `go tool kanna vet ./internal/feature/todo/usecase` runs them for a
package with no `//go:generate` line of its own. Before any runs, each is asked for its version: a generator that is not
a tool of the module, or a release from before its vet, stops them all, as a problem of a plan stops `kanna gen`.

The vets read what is generated as it is on disk, which is what compiles; whether that is up to date is for
`kanna gen -check` to say. In CI, run both:

```yaml
- run: go tool kanna gen -check
- run: go tool kanna vet
```

A module passing holds nothing the vets found; it does not prove there is nothing to find.

## How the order is worked out

Each generator answers `-deps` with what a run reads and writes, and the module's hand-written files say what imports
what. A task comes after what writes into a package it reads. What generators wrote is left out of all of it, so that a
plan is the same before they have run and after.

Two tasks writing into a package they both read are told apart by what the code calls: a task checks that code once its
output is in place, so it comes after what writes what the code calls. When the code calls what both write, no order
compiles, and `go generate` cannot get through it from nothing. `kanna gen` runs one first and tells it the other's
names are coming, and the last to run finds them there, or reports them.

## Developing the family

[`DEVELOPING.md`](DEVELOPING.md) says how to change the family across repositories: the workspace of every checkout in

## Earlier versions of this module

`github.com/go-kanna/kanna` used to be another module, kanna v0.2.x with the first kanna-orm. Its versions, v0.0.1 to
v0.2.0, stay in the Go module proxy, retracted so that `go get` warns of them, and its code on the
[`archive/v0.2`](https://github.com/go-kanna/go-kanna.github.io/tree/archive/v0.2) branch of the site's repository. The
`kanna` command starts above them, at v0.3.0.
